# 一、前端页面原型说明书

## 1.1 文档目的

本文档用于说明 CampusFlow 前端原型页面的功能定位、页面结构、核心交互、状态变化与跳转关系，为 MockPlus 原型设计、前端开发和测试验收提供统一依据。

## 1.2 设计目标

CampusFlow 前端设计遵循以下原则：

1. **流程清晰**：用户能快速完成“发现活动—组队—报名—审核—签到—反馈”。
2. **交互直观**：重要操作按钮突出，状态反馈及时明确。
3. **视觉统一**：页面组件、色彩、间距、图标风格一致。
4. **移动友好**：支持后续适配移动端或小程序端。
5. **角色区分明确**：学生、队长、组织者、管理员看到的功能入口不同。

## 1.3 视觉规范

- 主色：蓝色 `#3B82F6`
- 辅色：紫色 `#8B5CF6`
- 成功色：绿色 `#22C55E`
- 警告色：橙色 `#F59E0B`
- 失败色：红色 `#EF4444`
- 页面圆角：12px
- 主按钮：实心蓝色按钮
- 次按钮：白底描边按钮
- 卡片阴影：轻阴影，悬停增强
- 字号层级：
  - 一级标题：24px
  - 二级标题：20px
  - 模块标题：18px
  - 正文：14px/16px
  - 辅助文字：12px

## 1.4 全局交互规范

- 表单输入错误时就地提示
- 危险操作必须二次确认
- 成功操作使用轻提示或成功弹窗
- 列表加载显示 skeleton/loading
- 空数据页给出引导文案
- 按钮禁用时需说明原因
- 页面切换采用淡入动画
- 卡片 hover 上浮 4px，增强可点击感

## 1.5 页面原型说明

------

### 页面 A：活动首页

**页面名称**：活动首页
 **页面路径**：`/activities`

### 页面目标

帮助学生快速发现可参与的校园活动。

### 页面模块

1. 顶部导航栏
    Logo、搜索框、活动分类、消息入口、个人中心
2. Banner 区
    展示推荐活动、热门活动或近期活动
3. 筛选区
    活动类型、时间区间、是否组队、报名状态
4. 活动列表区
    以卡片形式展示活动封面、标题、时间地点、状态、标签
5. 分页区
    支持翻页或加载更多

### 核心交互

- 点击活动卡片进入活动详情页
- 输入关键词后搜索活动
- 筛选条件变化时刷新列表
- 鼠标悬停卡片显示轻微上浮动效
- 点击“立即报名”跳转活动详情页

### 页面状态

- 默认状态：展示最新活动列表
- 搜索状态：展示关键词结果
- 空结果状态：显示“暂无符合条件的活动”
- 加载状态：显示占位骨架屏

### 跳转关系

- 活动首页 → 活动详情页
- 活动首页 → 通知页
- 活动首页 → 个人中心

------

### 页面 B：活动详情页

**页面名称**：活动详情页
 **页面路径**：`/activities/{id}`

### 页面目标

帮助用户全面了解活动并决定是否参与。

### 页面模块

1. 活动基础信息
    标题、封面、主办方、时间、地点、报名截止时间
2. 活动介绍区
    图文介绍、活动流程、注意事项
3. 报名规则区
    是否组队、队伍人数限制、报名条件
4. 操作区
    创建队伍、加入队伍、收藏活动、查看我的队伍
5. 评论/反馈区
    可展示历史活动评价或注意事项

### 核心交互

- 若活动需要组队，则显示“创建队伍/加入队伍”
- 若用户已报名，则显示当前状态
- 若活动已截止，则禁用报名相关按钮
- 点击“创建队伍”进入创建队伍页
- 点击“申请加入队伍”进入队伍申请页

### 页面状态

- 未登录：提示先登录
- 可报名：显示主要操作按钮
- 已报名：显示报名状态
- 已截止：显示截止提示
- 已满员：显示人数已满提示

### 跳转关系

- 活动详情页 → 创建队伍页
- 活动详情页 → 申请加入队伍页
- 活动详情页 → 我的队伍页

------

### 页面 C：创建队伍页

**页面名称**：创建队伍页
 **页面路径**：`/teams/create`

### 页面目标

帮助学生快速创建参与活动的队伍。

### 页面模块

1. 队伍信息表单
    队伍名称、队伍口号、队伍简介、目标活动
2. 队伍规则说明
    展示当前活动允许的队伍人数范围
3. 操作区
    提交创建、取消返回

### 核心交互

- 表单必填校验
- 队伍名称重复校验
- 创建成功后自动生成邀请码
- 创建成功后跳转队伍详情页

### 页面状态

- 正常创建状态
- 表单校验失败状态
- 创建成功状态

### 跳转关系

- 创建队伍页 → 队伍详情页
- 创建队伍页 → 活动详情页

------

### 页面 D：队伍详情页

**页面名称**：队伍详情页
 **页面路径**：`/teams/{id}`

### 页面目标

供队长和成员查看队伍状态、管理成员、提交报名。

### 页面模块

1. 队伍基本信息
    队名、队长、活动、简介、邀请码
2. 成员列表
    成员头像、昵称、角色、加入时间
3. 入队申请区
    显示申请人、申请理由、处理按钮
4. 队伍操作区
    邀请成员、移除成员、转让队长、提交报名

### 核心交互

- 队长可批准/拒绝申请
- 人数不足时禁用“提交报名”
- 点击邀请成员可复制邀请码/链接
- 提交报名时弹出确认框

### 页面状态

- 队长视角：显示完整管理功能
- 普通成员视角：仅查看队伍信息
- 报名已提交：隐藏提交按钮，显示审核中
- 审核通过：显示报名成功状态

### 跳转关系

- 队伍详情页 → 报名状态页
- 队伍详情页 → 活动详情页

------

### 页面 E：加入队伍页

**页面名称**：加入队伍页
 **页面路径**：`/teams/join`

### 页面目标

帮助学生查找并申请加入已有队伍。

### 页面模块

1. 队伍筛选区
    队伍名称、活动名称、人数缺口
2. 队伍列表区
    队伍名、队长、目标活动、当前人数、简介
3. 申请表单弹窗
    输入申请理由

### 核心交互

- 点击“申请加入”弹出理由输入框
- 已申请显示“审核中”
- 已满员不可申请
- 申请成功后不跳页，仅提示成功

### 页面状态

- 正常可申请
- 已申请审核中
- 已加入其他队伍
- 队伍满员

### 跳转关系

- 加入队伍页 → 队伍详情页
- 加入队伍页 → 活动详情页

------

### 页面 F：报名审核页（组织者端）

**页面名称**：报名审核页
 **页面路径**：`/organizer/reviews`

### 页面目标

帮助组织者高效审核个人/队伍报名信息。

### 页面模块

1. 顶部筛选
    待审核、已通过、已驳回、活动名称筛选
2. 报名列表表格
    报名对象、活动名称、申请时间、状态
3. 详情抽屉
    展示报名队伍详情、成员信息、申请说明
4. 操作区
    通过、驳回、备注

### 核心交互

- 点击表格行打开详情抽屉
- 驳回必须填写理由
- 审核后自动发送通知
- 支持批量通过/驳回

### 页面状态

- 默认待审核列表
- 已处理列表
- 空数据状态
- 审核完成状态

### 跳转关系

- 审核页 → 活动详情页
- 审核页 → 通知页

------

### 页面 G：通知页

**页面名称**：通知页
 **页面路径**：`/notices`

### 页面目标

统一承载报名结果、活动提醒、系统公告。

### 页面模块

1. 消息分类标签
    全部、未读、报名结果、活动提醒、系统公告
2. 消息列表
    标题、摘要、时间、状态标签
3. 操作区
    标记已读、一键已读、删除

### 核心交互

- 点击消息查看详情
- 未读消息显示红点
- 支持实时更新未读数
- 高优先级消息置顶显示

### 页面状态

- 有未读消息
- 全部已读
- 空消息状态

### 跳转关系

- 通知页 → 活动详情页
- 通知页 → 队伍详情页

------

### 页面 H：签到页

**页面名称**：活动签到页
 **页面路径**：`/sign`

### 页面目标

完成活动现场签到和状态反馈。

### 页面模块

1. 活动信息展示
    活动标题、时间、地点
2. 签到方式
    二维码签到 / 输入签到码
3. 签到结果反馈区
    成功、重复签到、签到失败原因

### 核心交互

- 输入签到码后提交
- 签到成功显示绿色反馈
- 重复签到显示灰色说明
- 非签到时间段提示不可签到

### 页面状态

- 未签到
- 签到成功
- 重复签到
- 签到时间失效

### 跳转关系

- 签到页 → 活动结果页
- 签到页 → 通知页

------

### 页面 I：反馈页

**页面名称**：活动反馈页
 **页面路径**：`/feedback/{activityId}`

### 页面目标

收集参与者对活动的评分与建议。

### 页面模块

1. 活动摘要
    活动标题、时间、参与身份
2. 评分区
    星级评分
3. 文字反馈区
    文本输入框
4. 快捷标签区
    流程清晰、通知及时、组织有序等

### 核心交互

- 评分必填
- 提交后不可重复评价
- 提交成功显示感谢页

### 页面状态

- 未反馈
- 已反馈
- 提交成功

### 跳转关系

- 反馈页 → 活动详情页
- 反馈页 → 首页

# 二、后端数据库 E-R 设计说明

## 2.1 设计目标

数据库设计应满足以下要求：

1. 支撑活动、队伍、报名、审核、通知、签到、反馈等核心业务
2. 结构清晰，便于后续扩展
3. 避免冗余，保持较好的规范化
4. 兼顾查询效率和课程项目实现难度

------

## 2.2 核心实体说明

------

### 实体 1：User（用户）

用于存储平台用户基本信息。

**主要属性**

- `id`：用户主键
- `username`：登录账号
- `password`：加密密码
- `nickname`：昵称
- `avatar`：头像地址
- `email`：邮箱
- `role_id`：角色 ID
- `status`：账号状态
- `created_at`：创建时间

**说明**
 一个用户只对应一个主角色，但后续可以扩展为多角色。

------

### 实体 2：Role（角色）

定义系统中的角色类型。

**主要属性**

- `id`
- `role_name`

**典型角色**

- student
- captain
- organizer
- admin

------

### 实体 3：Activity（活动）

存储校园活动信息。

**主要属性**

- `id`
- `title`
- `cover_url`
- `description`
- `organizer_id`
- `type`
- `location`
- `start_time`
- `end_time`
- `signup_deadline`
- `require_team`
- `min_team_size`
- `max_team_size`
- `status`

**说明**
 一个活动由一个组织者发布，但一个组织者可以发布多个活动。

------

### 实体 4：Team（队伍）

用于存储某活动下的报名队伍。

**主要属性**

- `id`
- `activity_id`
- `team_name`
- `leader_id`
- `slogan`
- `description`
- `invite_code`
- `status`
- `created_at`

**说明**
 一个活动可对应多个队伍；一个队伍只属于一个活动。

------

### 实体 5：TeamMember（队伍成员）

用于描述用户与队伍的多对多关系。

**主要属性**

- `id`
- `team_id`
- `user_id`
- `member_role`
- `join_status`
- `joined_at`

**说明**
 一个用户可加入多个不同活动的队伍，但同一活动中只能属于一个队伍。

------

### 实体 6：Application（申请/报名）

用于记录入队申请和正式报名申请。

**主要属性**

- `id`
- `activity_id`
- `team_id`
- `applicant_id`
- `type`
- `status`
- `reason`
- `reviewed_by`
- `reviewed_at`
- `review_comment`
- `created_at`

**说明**
 `type` 可区分：

- join_team：加入队伍申请
- signup_team：队伍报名申请

------

### 实体 7：Notification（通知）

用于记录系统通知、审核结果、活动提醒等消息。

**主要属性**

- `id`
- `user_id`
- `title`
- `content`
- `type`
- `is_read`
- `created_at`

------

### 实体 8：SignRecord（签到记录）

用于记录用户参加活动的签到状态。

**主要属性**

- `id`
- `activity_id`
- `user_id`
- `sign_type`
- `sign_time`
- `status`

------

### 实体 9：Feedback（反馈）

记录用户对活动的评价和意见。

**主要属性**

- `id`
- `activity_id`
- `user_id`
- `score`
- `content`
- `created_at`

------

### 实体 10：Announcement（公告）

用于管理员发布全站或活动相关公告。

**主要属性**

- `id`
- `title`
- `content`
- `created_by`
- `created_at`

------

## 2.3 实体关系说明

### 1. User 与 Role

- 一个 Role 对应多个 User
- 一个 User 属于一个 Role

关系：**Role 1 —— N User**

------

### 2. User 与 Activity

- 一个组织者可以发布多个活动
- 一个活动只由一个组织者创建

关系：**User 1 —— N Activity**

其中 `Activity.organizer_id` 关联 `User.id`

------

### 3. Activity 与 Team

- 一个活动可以有多个队伍
- 一个队伍只属于一个活动

关系：**Activity 1 —— N Team**

------

### 4. User 与 Team

- 一个用户可以加入多个不同活动的队伍
- 一个队伍可以有多个成员

关系：**User N —— N Team**
 通过中间实体 `TeamMember` 实现

------

### 5. Team 与 TeamMember

- 一个队伍有多个成员记录
- 一个成员记录只对应一个队伍

关系：**Team 1 —— N TeamMember**

------

### 6. User 与 TeamMember

- 一个用户可以产生多条队伍成员记录
- 一条成员记录只属于一个用户

关系：**User 1 —— N TeamMember**

------

### 7. Activity / Team / User 与 Application

- 一个活动可有多条申请记录
- 一个队伍可有多条申请记录
- 一个用户可提交多条申请记录

关系：

- **Activity 1 —— N Application**
- **Team 1 —— N Application**
- **User 1 —— N Application**

------

### 8. User 与 Notification

- 一个用户可收到多条通知

关系：**User 1 —— N Notification**

------

### 9. Activity / User 与 SignRecord

- 一个活动有多条签到记录
- 一个用户有多条签到记录

关系：

- **Activity 1 —— N SignRecord**
- **User 1 —— N SignRecord**

------

### 10. Activity / User 与 Feedback

- 一个活动可有多条反馈
- 一个用户可提交多条反馈

关系：

- **Activity 1 —— N Feedback**
- **User 1 —— N Feedback**

------

```
Role 1 ----- N User
User 1 ----- N Activity
Activity 1 ----- N Team
User N ----- N Team   (via TeamMember)
Activity 1 ----- N Application
Team 1 ----- N Application
User 1 ----- N Application
User 1 ----- N Notification
Activity 1 ----- N SignRecord
User 1 ----- N SignRecord
Activity 1 ----- N Feedback
User 1 ----- N Feedback
User 1 ----- N Announcement
```

------

## 2.5 主键与外键设计建议

### 主键

所有主表统一使用：

- `BIGINT` 自增 或 雪花 ID

### 外键

- `user.role_id -> role.id`
- `activity.organizer_id -> user.id`
- `team.activity_id -> activity.id`
- `team.leader_id -> user.id`
- `team_member.team_id -> team.id`
- `team_member.user_id -> user.id`
- `application.activity_id -> activity.id`
- `application.team_id -> team.id`
- `application.applicant_id -> user.id`
- `application.reviewed_by -> user.id`
- `notification.user_id -> user.id`
- `sign_record.activity_id -> activity.id`
- `sign_record.user_id -> user.id`
- `feedback.activity_id -> activity.id`
- `feedback.user_id -> user.id`
- `announcement.created_by -> user.id`

------

## 2.6 索引设计建议

建议建立如下索引：

- `activity(title, status, signup_deadline)`
- `team(activity_id, leader_id)`
- `team_member(team_id, user_id)`
- `application(activity_id, status, type)`
- `notification(user_id, is_read)`
- `sign_record(activity_id, user_id)`
- `feedback(activity_id, user_id)`

------

## 2.7 数据库设计说明总结

本数据库设计以活动为核心，以队伍协作和报名审核为主线，通过 Team、TeamMember、Application 三类实体建立活动参与闭环，通过 Notification、SignRecord、Feedback 扩展活动全流程管理能力，整体满足课程项目的功能需求、扩展性需求和答辩展示需求。

```
Authorization: Bearer {token}
Content-Type: application/json
```

### 请求参数

#### Body 参数

| 参数名      | 类型   | 必填 | 说明     |
| ----------- | ------ | ---- | -------- |
| activityId  | Long   | 是   | 活动 ID  |
| teamName    | String | 是   | 队伍名称 |
| slogan      | String | 否   | 队伍口号 |
| description | String | 否   | 队伍简介 |

### 请求示例

```
{
  "activityId": 1001,
  "teamName": "Campus Masters",
  "slogan": "协作赢未来",
  "description": "我们是一支专注创新与执行的学生团队"
}
```

### 返回结果

#### 成功响应

```
{
  "code": 200,
  "message": "创建成功",
  "data": {
    "teamId": 501,
    "inviteCode": "ABCD1234"
  }
}
```

#### 失败响应

```
{
  "code": 400,
  "message": "当前活动不允许组队",
  "data": null
}
```

### 业务规则

1. 活动必须存在
2. 活动必须允许组队
3. 用户不能重复创建同活动队伍
4. 队伍名称不能为空

### 错误码说明

| 错误码 | 含义                    |
| ------ | ----------------------- |
| 200    | 成功                    |
| 400    | 参数错误 / 业务校验失败 |
| 401    | 未登录或 token 无效     |
| 403    | 无权限                  |
| 404    | 资源不存在              |
| 500    | 服务器内部错误          |

## 3.5 接口验收标准建议

每个接口在报告或测试文档中都建议补这三项：

1. **功能是否完成**
    例如：创建队伍后是否返回 teamId 和 inviteCode
2. **边界是否处理**
    例如：重复申请、人数已满、活动截止后是否禁止操作
3. **异常是否友好**
    例如：返回明确错误信息，而不是笼统失败
