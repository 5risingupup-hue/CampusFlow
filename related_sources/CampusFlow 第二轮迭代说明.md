# CampusFlow 第二轮迭代说明

## 1. 迭代目标

第二轮迭代围绕第一轮演示反馈展开，目标是把 CampusFlow 从“活动发现、组队报名、审核、签到、反馈”的基础闭环，推进为更完整的校园活动协作平台。

本轮重点解决五类问题：

1. 非组队活动缺少明确的个人报名与审核流程。
2. 组队活动的业务语义不清晰，演示数据曾把学生自动放入 Bob 的队伍，容易误解为“系统自动组队”或“只有固定队长能报名”。
3. 队伍创建后缺少成员退出、移除、队长转让和解散等真实管理动作。
4. 活动状态虽然存在字段，但组织者缺少可操作的生命周期流转入口。
5. 需求获取、OO 分析和验收材料需要与实现保持一致，便于后续实验报告和答辩。

| 角色 | 反馈问题 | 对应改进 |
| --- | --- | --- |
| 学生 | 个人参与型活动不需要组队，但页面只有组队入口，报名路径不清晰。 | 增加个人报名入口，生成 `signup_personal` 审核记录。 |

| 组织者 | 活动发布后需要快速关闭报名、结束活动或取消活动。 | 增加活动状态流转接口和管理页操作。 |
| 管理员/助教 | 需求、OO 模型和实际功能之间需要形成可追踪关系。 | 补充用户故事、需求变更表、对象模型和状态模型。 |

## 3. 需求变更表

| 原需求 | 变更原因 | 第二轮修改 |
| --- | --- | --- |
| 活动报名主要依赖队伍提交。 | 校园活动存在讲座、培训、体验课等个人参与场景。 | 新增个人报名申请类型 `signup_personal`。 |
| 组队演示数据预置大量 Bob 队长队伍，并把 Alice 自动加入。 | 这会让用户误以为系统会自动组队，或只有固定队长可以报名。 | 移除自动加入 Bob 队伍的预置关系；改为招募中的示例队伍，用户需主动创建或申请加入。 |
| 组队入口不够明确。 | 用户需要先看到有哪些队伍、队伍还缺几个人，再决定创建或加入。 | 将导航入口改为“队伍广场”，活动卡片和详情页引导到创建队伍或队伍广场。 |
| 队伍详情只展示成员和审核申请。 | 真实协作中需要维护队伍成员关系。 | 新增退出、移除、转让队长、解散队伍。 |
| 活动状态字段主要靠编辑表单维护。 | 组织者需要快速执行状态流转。 | 新增 `/api/activities/{id}/status` 和管理页“变更状态”。 |
| 审核中心只处理队伍报名。 | 个人报名也需要统一审核。 | 审核中心增加报名类型展示，兼容个人报名和队伍报名。 |

## 4. OO 分析补充

### 4.1 核心类与职责

| 类/对象 | 关键属性 | 主要职责 |
| --- | --- | --- |
| `User` | `id`、`username`、`nickname`、`role` | 表示学生、队长、组织者、管理员等系统用户。 |
| `Activity` | `status`、`requireTeam`、`signupDeadline`、`signCode` | 管理活动信息、报名规则、签到窗口和状态流转。 |
| `Team` | `leaderId`、`status`、`inviteCode` | 管理组队报名过程；创建队伍的用户自动成为队长。 |
| `TeamMember` | `memberRole`、`joinStatus` | 表示用户在队伍中的身份和加入状态。 |
| `ApplicationRecord` | `type`、`status`、`reviewedBy` | 统一承载入队申请、队伍报名、个人报名三类审核流。 |
| `Notification` | `type`、`isRead` | 承载审核、队伍、活动生命周期和公告通知。 |
| `SignRecord` | `status`、`signTime` | 记录活动签到资格与签到结果。 |
| `Feedback` | `score`、`tags`、`willingRejoin` | 记录活动结束后的参与反馈。 |

### 4.2 类之间的主要关系

- 一个 `Activity` 由一个组织者 `User` 创建。
- 一个 `Activity` 可以有多个 `Team`，也可以有多个个人 `ApplicationRecord`。
- 一个 `Team` 包含多个 `TeamMember`，其中一个成员的 `memberRole` 为 `leader`；队伍创建者即初始队长。
- 用户申请加入已有队伍时，先生成 `ApplicationRecord(type=join_team)` 和待审核 `TeamMember`；队长审核通过后才成为正式队员。
- `ApplicationRecord` 通过 `type` 区分 `join_team`、`signup_team`、`signup_personal`。
- 审核通过的 `signup_team` 会为队伍成员生成 `SignRecord`。
- 审核通过的 `signup_personal` 会为申请人生成 `SignRecord`。
- 重要业务动作会生成 `Notification`，用于通知相关用户。

### 4.3 状态模型

#### Activity 状态

```text
draft -> published -> signup_open -> signup_closed -> finished
                     \-> cancelled
published -----------> cancelled
signup_open ---------> cancelled
signup_closed -------> cancelled
```

#### Team 状态

```text
creating -> forming -> submitted -> approved
                   |            -> rejected
                   -> disbanded
rejected ----------> submitted
```

#### ApplicationRecord 状态

```text
pending -> approved
pending -> rejected
```

#### TeamMember 状态

```text
pending -> approved
pending -> rejected
approved -> left
approved -> removed
pending/approved -> disbanded
```

## 5. 顺序图文字说明

### 5.1 个人报名

1. 学生进入个人参与活动详情页。
2. 前端根据 `canSignupPersonal` 显示“提交个人报名”。
3. 学生提交报名说明。
4. 后端创建 `ApplicationRecord(type=signup_personal, status=pending)`。
5. 后端给活动组织者生成待审核通知。
6. 组织者在审核中心通过报名。
7. 后端更新申请状态为 `approved`，并创建 `SignRecord(status=unsigned)`。
8. 学生收到报名通过通知，后续可签到。

### 5.2 队伍成员维护

1. 队长进入队伍详情页。
2. 队长选择移除成员或转让队长。
3. 后端校验队伍未提交/未通过报名，并校验当前用户为队长。
4. 后端更新 `TeamMember` 或 `Team.leaderId`。
5. 后端发送队伍变更通知。
6. 前端重新加载队伍详情，展示最新成员关系。

### 5.3 创建队伍并报名

1. 学生进入报名中的组队活动详情页。
2. 前端显示“创建队伍并发起招募”和“查找队伍并申请加入”两个入口。
3. 学生选择创建队伍，填写队伍名称、口号和简介。
4. 后端创建 `Team(status=forming)`，并创建 `TeamMember(memberRole=leader, joinStatus=approved)`。
5. 创建者进入队伍详情页，等待其他同学申请加入或直接维护队伍资料。
6. 队伍人数满足活动要求后，队长点击“提交队伍报名”。
7. 后端创建 `ApplicationRecord(type=signup_team, status=pending)`，并通知组织者审核。

### 5.4 申请加入队伍

1. 学生进入“队伍广场”。
2. 前端展示招募中的队伍、所属活动、队长、当前人数、最大人数和剩余席位。
3. 学生选择队伍并填写申请理由。
4. 后端创建 `ApplicationRecord(type=join_team, status=pending)` 和待审核队伍成员记录。
5. 队长在队伍详情页通过申请。
6. 后端将申请人 `TeamMember.joinStatus` 改为 `approved`，申请人成为队员。

### 5.5 活动状态流转

1. 组织者进入活动管理页。
2. 组织者选择目标状态。
3. 后端校验组织者权限与目标状态合法性。
4. 后端更新 `Activity.status`。
5. 若活动取消或结束，后端向相关参与者发送通知。
6. 前端刷新活动列表和状态标签。

## 6. 本轮新增接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/activities/{id}/signup` | 提交个人报名。 |
| `POST` | `/api/activities/{id}/status` | 变更活动状态。 |
| `GET` | `/api/teams/joinable` | 查询队伍广场可加入队伍，包含队长、人数、剩余席位和申请状态。 |
| `POST` | `/api/teams` | 创建队伍，当前登录用户自动成为队长。 |
| `POST` | `/api/teams/{id}/leave` | 普通成员退出队伍。 |
| `POST` | `/api/teams/{id}/disband` | 队长或管理员解散队伍。 |
| `POST` | `/api/teams/{id}/transfer` | 队长转让队长身份。 |
| `POST` | `/api/teams/{id}/members/{userId}/remove` | 队长移除成员。 |

## 7. 验收路径

### 学生个人报名

1. 使用 `student02 / 123456` 登录。
2. 找到个人参与且报名中的活动。
3. 点击“提交个人报名”。
4. 使用 `organizer01 / 123456` 登录审核中心，通过该个人报名。
5. 切回学生账号，进入签到页查看该活动已具备签到资格。

### 队伍管理

1. 使用 `student01 / 123456` 登录。
2. 进入报名中的组队活动详情页，点击“创建队伍并发起招募”。
3. 创建成功后进入队伍详情页，确认 Alice 是队长。
4. 使用其他学生账号进入“队伍广场”，查看该队伍的队长、当前人数和剩余席位。
5. 其他学生提交入队申请。
6. 切回 Alice，在队伍详情页通过申请，确认申请人成为队员。
7. Alice 在队伍详情页提交队伍报名，组织者在审核中心处理。

### 队伍广场

1. 使用任意学生账号登录。
2. 点击顶部导航“队伍广场”。
3. 查看招募中队伍列表，确认页面展示队伍名称、活动名称、队长、当前人数和剩余席位。
4. 如果当前用户已在某个队伍中，该队伍按钮显示“进入队伍”；如果可申请，则显示“申请加入”。

### 活动状态管理

1. 使用 `organizer01 / 123456` 登录。
2. 进入“活动发布与管理”。
3. 对活动执行“报名截止”“已结束”或“已取消”状态变更。
4. 查看活动详情和通知中心，确认状态与通知同步更新。

## 8. 迭代回顾

第二轮迭代将需求获取中暴露的“个人参与缺口”“组队语义缺口”“队伍管理缺口”和“活动生命周期缺口”落到了可运行功能上。组队逻辑明确为“创建队伍者是队长，申请加入者是队员”，并通过队伍广场展示队伍供需关系；同时把 `ApplicationRecord` 作为统一审核对象，避免为个人报名另起一套流程。这样系统对象模型更稳定，审核中心也保持单一入口，便于第三轮继续扩展持久化、操作日志和权限粒度控制。
